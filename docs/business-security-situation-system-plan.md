# 业务安全态势系统建设思路与方案

> 文档用途：会议讨论稿
>
> 说明：本文中的事件等级、上报时限、建设阶段和验收指标均为建议基线。正式执行时，应以国家法律法规、上级单位要求和本单位现行制度为准，并由主管部门审批发布。

## 1. 建设结论

业务安全态势系统应建设为面向全域安全运营和业务保障的统一平台，核心目标不是“展示更多图表”，而是回答四个问题：

1. 当前系统和业务是否正常，哪些风险正在上升？
2. 异常发生在哪里，影响了哪些业务、人员、终端、资产和数据？
3. 谁在什么时限内负责研判、上报、处置和恢复？
4. 处置是否有效，是否形成了可审计、可复盘、可改进的闭环？

总体闭环：

```text
多源数据接入
    -> 数据归一与质量校验
    -> 五域态势分析与告警聚合
    -> 事件研判、登记与分级
    -> 分级上报与应急响应
    -> 处置、恢复验证与事件关闭
    -> 报告沉淀、复盘整改与指标改进
```

建设原则：

- 统一标准：统一对象、事件、等级、状态、时间和指标口径。
- 事实可追溯：每个指标、告警和事件都能追溯到来源、原始记录和处理过程。
- 业务优先：以业务连续性、数据安全和任务影响作为风险判断的重要依据。
- 分级响应：不同影响程度使用不同的通知对象、响应力量和审批要求。
- 人机协同：机器负责采集、聚合、发现和提醒，人员负责确认、定级、决策和高风险处置。
- 最小权限：按职责授权，敏感数据、导出和高危动作均需授权并留痕。
- 先闭环后智能：先实现可靠的台账、报告和流程，再建设自动关联和自动编排。

## 2. 建设范围与系统边界

### 2.1 纳入范围

| 建设域 | 主要职责 | 重点对象 |
| --- | --- | --- |
| 综合态势 | 跨域汇总、统一研判、领导视图、重大事件总览 | 业务、安全、终端、运维总体状态 |
| 安全态势 | 安全威胁、漏洞、访问和数据风险分析 | 安全事件、账号、策略、漏洞、审计日志 |
| 业务态势 | 业务连续性和关键服务质量监测 | 业务系统、服务、接口、交易、队列、数据库 |
| 终端态势 | 终端健康、人员关联和终端安全行为分析 | 终端、人员、账号、证书、外设、终端事件 |
| 运维态势 | 基础设施、主机、进程、资源和来源健康监测 | 主机、网络、进程、探针、运维告警 |
| 系统管理 | 账户、角色、审批、配置和审计治理 | 用户、权限、策略、操作、审批、审计日志 |
| 平台运行保障 | 平台可用性、数据源健康和数据质量治理 | 接入源、任务、接口、数据延迟、完整性 |

### 2.2 不纳入边界或需明确授权的内容

- 系统不替代各业务系统、安全设备、终端平台和运维平台的专业管理功能。
- 系统不直接保存不必要的文件原文、口令、密钥等高敏感内容；原则上保存元数据、摘要、证据引用和必要的脱敏信息。
- 系统不自动执行删除数据、隔离核心生产系统、批量禁用账号等高风险动作，除非经过明确授权、审批和可回退设计。
- 监管报送、涉密信息报送和对外通报须遵循现行制度，由授权人员审核发布。

### 2.3 业务对象关系

```text
人员 / 账号 <-> 终端 <-> 资产 / 主机 <-> 服务 / 业务系统 <-> 业务链路
        \             |             /             |
         \        安全事件       运维事件      业务事件
          \______________ 统一事件中心 ______________/
                              |
                     报告、预案、工单、审计
```

### 2.4 业务安全态势监控对象

第一批监控对象应围绕“人、端、网、应用、数据、事件、平台”建立对象台账。对象不是只用于展示名称，还要具备稳定 ID、责任人、所属组织、重要程度、关联关系和数据来源。

| 监控对象 | 当前业务例子 | 建议监控内容 | 主要关联 |
 | --- | --- | --- | --- |
 | 人员/账号 | 用户、业务负责人、值班人员、运维账号 | 在线/离线、登录成功/失败、异常时段、账号锁定、权限变化 | 人员、部门、终端、业务行为 |
 | 终端/装备 | PAD、办公终端、密盒、身份密钥、卫星终端 | 心跳、在线率、版本、证书、密码模块、外设、风险状态 | 人员、区域、业务软件 |
 | 区域/通信链路 | 北京中心、阿布扎比、新加坡、柏林等区域；地面/卫星链路 | 上下行速率、带宽利用率、时延、丢包、链路状态、切换状态 | 区域人员、终端、业务系统 |
 | 业务系统/服务 | 密信服务、签阅服务、密盒服务 | 可用性、请求量、成功率、错误率、响应时延、版本和变更 | 网关、数据库、链路、事件 |
 | 业务接口/关键链路 | 登录、消息发送/接收、文件上传/下载、签阅、归档、加解密 | 调用量、成功/失败、耗时、超时、重试、依赖状态 | 服务、交易、队列、数据库 |
 | 业务流程/文件 | 文件发起、接收、打开、会签、签批、补正、归档、下载、外发 | 流转量、待办量、停留时长、超时、退回、流转完整性 | 人员、账号、敏感级别、事件 |
 | 密码与证书 | PIN 校验、证书交换、一次一密、加密封装、解密校验 | 成功/失败、失败原因、证书有效期、重试和异常解密 | 终端、人员、文件、密盒服务 |
 | 数据库/基础设施 | 业务数据库、网关节点、主机、进程、存储 | CPU、内存、连接数、磁盘、队列、进程、主备和备份状态 | 业务服务、运维告警 |
 | 安全事件 | 异常登录、未知文件、异常下载、异常外联、策略命中 | 发生时间、对象、等级、证据、处置、恢复和关联事件 | 人员、终端、业务、运维 |
 | 数据源/平台 | 运维探针、终端平台、安全平台、业务日志、报表任务 | 最后上报时间、延迟、完整率、重复率、解析失败、任务状态 | 指标、报告、事件台账 |

监控对象至少分为三种状态：

- **正常**：数据持续更新，指标在基线范围内，业务链路可用。
- **关注**：指标偏离基线、局部降级或即将超期，需要值班跟踪和专业确认。
- **异常/故障**：影响业务、安全或数据可信度，需要登记事件并按等级响应。

业务态势不应只展示“系统在线”。例如签阅服务在线但签批节点平均停留 186 分钟、待办持续增加时，系统状态可以是“服务可用、业务能力降级”，应产生业务告警。
## 3. 角色与职责

| 角色 | 主要职责 | 关键权限边界 |
| --- | --- | --- |
| 领导/指挥人员 | 查看综合态势、批准重大响应和资源调度、确认重大事件结论 | 不直接修改原始数据和审计记录 |
| 态势值班人员 | 7×24 监测、告警确认、事件登记、初报和升级提醒 | 不单独执行超出授权范围的高危动作 |
| 业务责任人 | 判断业务影响、确认业务恢复、提供业务处置方案 | 只能处理授权业务范围 |
| 安全责任人 | 安全研判、证据保全、风险遏制、数据安全判断 | 高危策略变更按审批执行 |
| 运维责任人 | 主机、网络、数据库、应用基础设施处置和恢复 | 生产操作需遵守变更和双人复核要求 |
| 终端/资产责任人 | 终端隔离、设备核查、人员和资产归属确认 | 不越权查看无关人员敏感信息 |
| 系统管理员 | 用户、基础配置、接入配置和系统运行维护 | 不负责安全审批和审计复核 |
| 安全管理员 | 权限策略、安全配置、接入授权和高危动作审批 | 与系统管理员、审计管理员职责分离 |
| 审计管理员 | 查询登录、操作、审批和事件留痕，检查合规性 | 不修改业务处置结果和原始审计记录 |
| 数据提供方 | 保证来源数据的完整性、及时性和字段含义 | 负责数据质量问题整改 |

## 4. 统一数据与指标体系

### 4.1 统一数据分层

| 层级 | 内容 | 处理原则 |
| --- | --- | --- |
| 原始层 | 来源系统原始报文、日志、快照和批次 | 保留来源、批次、请求、采集时间和 schema 版本 |
| 标准层 | 统一的资产、人员、账号、服务、事件和指标对象 | 做字段映射、类型校验、时间归一和身份关联 |
| 分析层 | 告警聚合、趋势、风险评分、影响范围和关联关系 | 明确算法/规则版本，不覆盖原始事实 |
| 应用层 | 态势页面、报告、事件台账、预案、通知和审计 | 按角色授权，展示来源和数据覆盖范围 |

### 4.2 公共字段要求

所有接入来源尽量提供以下字段；不能提供的字段必须登记原因，不用默认值掩盖缺失：

| 对象 | 最小公共字段 |
| --- | --- |
| 来源 | `sourceSystem`、`sourceType`、`schemaVersion`、`requestId`/`batchId`、接入状态 |
| 时间 | 发生时间、发现时间、观测时间、接收时间、恢复时间；统一时区和格式 |
| 资产 | 内部资产 ID、外部资产 ID、资产类型、所属组织、环境、重要程度 |
| 人员/账号 | 内部人员 ID、外部人员 ID、账号 ID、组织、岗位；按权限脱敏 |
| 服务 | 服务 ID、业务系统、关键链路、依赖对象、SLA 目标 |
| 指标 | 指标编码、名称、数值、单位、统计口径、时间窗口、数据状态 |
| 事件 | 事件 ID、类型、来源、等级、状态、标题、对象、影响、证据引用 |
| 处置 | 责任人、动作、开始/完成时间、结果、工单/审批 ID、验证结论 |

### 4.3 指标治理要求

每个正式指标必须登记：指标编码、名称、业务含义、计算公式、统计范围、时间窗口、刷新频率、数据来源、权威系统、责任人、缺数表现、版本和生效时间。

指标管理规则：

- 同名但时间窗口、来源、去重规则不同的指标必须使用不同编码。
- “告警数”“事件数”“上报事件数”“应急事件数”不得混用。
- 指标应区分发生时间、发现时间和接入时间，避免延迟数据造成趋势误判。
- 数据源不可用、延迟超阈值或覆盖不足时，显示“数据不可用/覆盖不足”，不显示伪造的零值。
- 综合指数必须公开组成项、权重、计算周期和扣分规则，未经确认不使用 Mock 数值作为正式指标。

### 4.4 第一批业务指标建议

以下指标结合当前系统已有的密信、签阅、终端和境外通信对象整理，数值仅用于说明指标如何落地：

| 指标 | 计算口径 | 关注意义 | 建议频率 |
 | --- | --- | --- | --- |
 | 在线用户率 | 当前在线用户数 / 用户总数 | 反映人员和终端使用保障情况 | 5 分钟 |
 | 密信消息收发量 | 发送消息数 + 接收消息数，按消息 ID 去重 | 反映密信业务活跃度和收发是否异常 | 5 分钟/日报 |
 | 密信文件流转量 | 发送文件数 + 接收文件数，按文件事件统计 | 识别批量下发、失败和异常外发 | 5 分钟/日报 |
 | 签阅处理率 | 已处理数 / 收到数 | 反映签阅业务闭环程度 | 5 分钟/日报 |
 | 签阅积压量 | 待签收、会签、领导签批等未完成节点之和 | 识别流程瓶颈和超时风险 | 5 分钟 |
 | 节点平均停留时长 | 各流程节点完成时间 - 进入时间的平均值 | 定位待签收、会签或签批瓶颈 | 15 分钟 |
 | 业务服务成功率 | 成功请求数 / 总请求数；明确超时、重试是否计入 | 反映服务真实可用性 | 1 分钟/5 分钟 |
 | 业务链路时延 | P95 或约定分位数，不只看平均值 | 识别少量严重慢请求 | 1 分钟 |
 | 加解密成功率 | 成功加密/解密次数 / 总尝试次数 | 反映密盒、证书和密码模块可用性 | 5 分钟 |
 | 境外链路利用率 | `max(上行, 下行) / 带宽容量` | 识别拥塞、切换和业务影响 | 1 分钟 |
 | 终端在线率 | 在线终端数 / 纳管终端数 | 反映人员和装备保障覆盖 | 5 分钟 |
 | 数据源新鲜度 | 当前时间 - 来源最后观测时间 | 判断报告和态势数据是否可信 | 5 分钟 |

正式上线前应为每项指标补充权威来源、去重规则、统计时区、异常值处理、责任人和缺数表现。
## 5. 报告体系

三类报告使用同一套指标、事件台账和数据质量结果，只改变统计窗口、读者和分析深度。报告应支持草稿、审核、发布、撤回、版本、导出和访问留痕。

### 5.1 日报：面向值班和当日运行

建议固定内容：

1. **报告摘要**：统计周期、生成时间、数据覆盖情况、总体运行判断。
2. **总体状态**：五域健康状态、核心业务可用性、关键数据源状态。
3. **核心指标**：业务成功率/可用性、关键链路状态、安全告警、终端在线率、运维资源和平台接入健康度。
4. **事件清单**：当日新增、升级、恢复、未关闭和超时事件，标明责任人和当前状态。
5. **重点异常**：重大告警、重复异常、异常趋势、影响对象和已采取措施。
6. **数据质量**：未上报来源、采集延迟、字段缺失、重复数据和接口失败。
7. **值班事项**：待跟踪问题、临时措施、下一班次交接事项和次日关注点。

建议输出：每日固定时间自动生成，值班人员确认，必要时由专业责任人补充说明；发生重大事件时立即生成专项快报，不等待日报周期。

### 5.2 周报：面向运营管理和专业负责人

建议固定内容：

1. **本周结论**：总体态势、较上周变化、主要风险和管理判断。
2. **趋势分析**：核心业务可用性、关键性能、安全事件、终端风险、运维告警和数据源健康的七日趋势。
3. **事件分析**：事件数量、等级、来源、领域、重复发生、平均响应时间、平均恢复时间和及时处置率。
4. **重点问题**：未关闭、超期、重复、跨域关联和影响核心业务的事件。
5. **整改跟踪**：整改项、责任部门、计划完成时间、当前进度、延期原因和验证结果。
6. **覆盖与质量**：来源接入覆盖率、数据完整率、数据延迟、异常缺数和新增数据源。
7. **下周计划**：风险治理、配置变更、预案建设、演练计划和需协调资源。

### 5.3 月报：面向领导决策和治理评价

建议固定内容：

1. **综合安全态势**：五域总体评价、重大风险、关键业务保障情况和管理结论。
2. **重点业务运行**：核心业务可用性、SLA 达标率、关键链路、容量趋势和重大变更影响。
3. **安全风险治理**：重大安全事件、漏洞/告警、异常行为、数据安全、账号和策略治理情况。
4. **终端与资产治理**：资产底数、在线覆盖、风险终端、人员归属、补丁/证书/外设等治理情况。
5. **运维保障**：主机、网络、数据库、进程、资源、来源健康和故障恢复情况。
6. **事件与应急复盘**：重大事件时间线、根因、影响、响应及时性、恢复效果和改进措施。
7. **合规与审计**：权限、审批、关键操作、审计发现、整改闭环和证据留存情况。
8. **资源与计划**：容量、人员、预算、技术债务、下月重点项目和需领导决策事项。

### 5.4 周报样例（示例）

以下为便于会议理解的“业务安全态势周报”样稿。示例数据沿用当前演示中的人员、密信、签阅、终端和链路对象，仅用于说明报告长什么样，不能作为真实业务结论。

#### 业务安全态势周报

- **统计周期**：2026-08-04 00:00 至 2026-08-10 24:00
- **编制时间**：2026-08-11 09:00
- **数据覆盖**：人员/终端、密信、签阅、密盒、链路、运维和安全事件；业务系统真实接口覆盖情况需另行确认
- **总体结论**：本周核心业务总体可用，密信收发保持稳定；签阅处理率较上周下降，领导签批节点存在积压；3 张证书进入轮换窗口，9 个 USB Key 认证异常需持续跟踪；未发现达到 I/II 级的正式上报事件。

#### 一、核心指标

## 6. 异常事件上报体系

### 6.1 告警与事件分层

| 层级 | 定义 | 是否直接上报 |
| --- | --- | --- |
| 原始告警 | 来源系统产生的单条规则命中、状态变化或异常日志 | 先进入聚合和去重流程 |
| 研判事件 | 对一个或多条告警进行关联后形成的可解释异常 | 由值班/专业人员确认 |
| 正式上报事件 | 按制度需要向组织内上级、主管部门或相关责任方报告的事件 | 按等级和时限执行 |
| 应急事件 | 已达到启动专项响应条件，需要调度组织和资源处置的事件 | 立即启动对应预案 |

### 6.2 异常事件目录

| 类别 | 典型事件 |
| --- | --- |
| 业务连续性 | 核心业务不可用、业务成功率骤降、关键交易失败、队列积压、关键链路中断、SLA 持续不达标 |
| 数据安全 | 敏感数据疑似泄露、越权访问、异常下载/导出/解密、数据篡改、数据丢失、备份不可用 |
| 网络与安全防护 | 入侵攻击、恶意代码、异常外联、横向扫描、边界防护失效、关键安全策略失效 |
| 终端安全 | 批量终端离线、终端高危行为、未授权设备接入、证书/密码模块异常、外设违规、终端被入侵 |
| 基础设施运维 | 核心主机故障、数据库故障、存储不足、网络设备故障、资源耗尽、机房/电力/环境异常 |
| 数据源与数据质量 | 数据源中断、接入认证失败、数据延迟超标、字段缺失、重复/乱序、归一失败、指标不可计算 |
| 态势平台运行 | 平台不可用、核心接口失败、任务积压、报告生成失败、通知失败、审计留痕失败 |
| 管理与合规 | 高危操作未审批、权限越权、审计缺失、配置违规、整改超期、制度要求未落实 |

### 6.3 事件触发原则

满足以下任一条件，应从告警升级为事件并进入人工研判：

- 影响核心业务、关键链路或重要任务的可用性、完整性或时效性。
- 涉及敏感数据、重要账号、关键资产或大范围人员/终端。
- 同类告警短时间集中出现，存在扩散、横向移动或持续升级趋势。
- 关键安全防护、备份、审计或应急能力失效。
- 数据源或平台故障导致态势判断失真，且预计在一个报告周期内无法恢复。
- 现有制度明确要求上报，或责任人判断可能达到上报条件。

### 6.4 建议四级分级基线

| 建议等级 | 讨论名称 | 参考判定 | 建议初报时限 |
| --- | --- | --- | --- |
| I 级 | 特别重大 | 多个核心业务或大范围关键资产受影响；发生重大敏感数据泄露/破坏；影响持续扩大或需要统一指挥 | 发现后 10 分钟内；30 分钟内补充初步影响和措施 |
| II 级 | 重大 | 单个核心业务长时间不可用；关键安全防护失效；重要数据或关键账号存在明确风险；需要跨部门协同 | 发现后 30 分钟内；2 小时内补充研判信息 |
| III 级 | 较大 | 重要业务或局部区域受影响；多台终端/主机异常；有明确安全风险但范围可控 | 发现后 2 小时内；当日形成处置进展 |
| IV 级 | 一般 | 单点、低影响、可快速恢复的异常；不满足正式升级条件但需要留痕和跟踪 | 纳入当日台账或日报；超时未恢复再升级 |

分级不是只看告警数量，应综合判断：影响范围、持续时长、业务重要性、数据敏感程度、完整性/保密性/可用性影响、扩散可能性、处置难度和外部影响。任何等级均可越级上报，任何自动分级都必须允许人工调整并记录理由。

### 6.5 初报、续报、终报和越级规则

- **初报**：先报告已确认事实、发现时间、影响对象、初步等级、当前措施和待核实内容；不因信息不完整而延误。
- **续报**：在影响范围、根因、处置动作、风险等级或恢复进度发生重要变化时更新；I/II 级按固定间隔续报，建议不超过 2 小时一次。
- **终报**：业务和安全影响已恢复或风险已受控，完成影响评估、根因判断、证据整理、遗留风险和后续整改安排后提交。
- **越级上报**：无法在规定时间内确认等级、影响持续扩大、责任部门无法及时响应、跨域影响明显、涉及敏感数据或可能触发监管要求时，先按高一级临时上报，再补充确认。
- **时限计算**：以首次发现时间为起点；来源延迟、值班交接或等待完整证据不能作为延迟初报的理由。

以下是第一批可讨论的告警规则。阈值是建议基线，正式值应根据业务基线、SLA、历史分布和误报率校准；单条告警不一定直接形成正式上报事件。

| 监控对象 | 告警示例 | 建议触发条件 | 初始等级 | 首要动作 |
 | --- | --- | --- | --- | --- |
 | 密信服务 | 消息发送失败率升高 | 5 分钟失败率 > 5%，或连续 5 次调用失败 | III/关注 | 检查服务、网关、数据库和链路，抽样验证收发 |

告警文案应包含“对象 + 现象 + 时间 + 当前值/阈值 + 影响 + 已采取动作”，例如：

> `签阅服务 / 领导签批节点：平均停留 186 分钟，建议阈值 120 分钟，当前待办 11 份，已连续 3 个周期上升；业务保障组已启动催办，暂未影响服务可用性。`

> `终端 PAD / RY-005：连续 3 次 PIN 校验失败，发生于 2026-08-09 14:32，已限制后续尝试；需核验人员身份、终端状态和密钥介质。`

> `境外共享链路 / 阿布扎比：下行 42 Mbps，占 50 Mbps 带宽 84%，持续 12 分钟；已进入关注区间，建议检查批量文件传输和备用链路。`

告警转事件的关键判断是“是否需要责任人、时限和处置动作”。同一告警重复出现应聚合为一个事件，恢复后记录恢复时间；不能因为告警自动恢复就跳过影响确认和复盘。
## 7. 事件必填信息和生命周期

### 7.1 事件必填信息

| 信息组 | 必填内容 |
 | --- | --- |
 | 基本信息 | 事件编号、标题、事件类型、来源系统、来源事件 ID、报告版本 |
 | 时间信息 | 发生时间、发现时间、接入时间、当前更新时间、恢复时间（已知时填写） |
 | 分级信息 | 初始等级、当前等级、判定依据、升级/降级记录、是否需要正式上报 |
 | 影响信息 | 受影响业务、服务、资产、主机、终端、人员/账号、区域、影响范围和数量 |
 | 影响判断 | 可用性、完整性、保密性、业务时效、数据风险、外部影响和预计损失 |
 | 事实证据 | 日志/告警引用、指标截图或快照引用、时间线、关联事件、原始报文索引 |
 | 处置信息 | 当前措施、责任部门、责任人、协同部门、工单/审批编号、下一步计划 |
 | 状态信息 | 研判状态、上报状态、响应状态、处置状态、恢复状态、关闭状态 |
 | 结案信息 | 恢复时间、验证方法、验证人、遗留风险、根因、整改项和复盘结论 |

### 7.2 事件生命周期

```text
发现 -> 去重/聚合 -> 研判确认 -> 登记 -> 分级
  -> 上报 -> 响应 -> 处置 -> 恢复验证 -> 关闭 -> 复盘整改
```

状态规则：

1. **发现**：自动接收来源告警、人工发现或外部通报。
2. **去重/聚合**：按事件 ID、对象、时间窗口、规则和关联关系合并重复告警；保留原始告警引用。
3. **研判确认**：值班人员确认是否为真实异常，误报要说明理由，不能静默删除。
4. **登记/分级**：形成统一事件编号，补齐影响对象、等级和责任人。
5. **上报**：根据等级和制度通知相关对象，记录送达状态、接收人和版本。
6. **响应/处置**：执行预案或工单动作，所有关键动作、审批和结果留痕。
7. **恢复验证**：由业务责任人和技术责任人共同确认服务、数据、权限和安全状态恢复。
8. **关闭**：满足关闭条件后由授权人员关闭；未解决但暂时缓解的事件不能直接关闭。
9. **复盘整改**：重大和重复事件必须形成根因、改进项、责任人和完成期限，并跟踪验证。

自动化边界：自动化可以完成接收、校验、去重、聚合、阈值触发、通知提醒和报告取数；事件定级、正式上报、影响确认、敏感数据判断、生产隔离和最终关闭原则上保留人工确认。

## 8. 应急预案体系

### 8.1 首批预案目录

| 预案编号 | 场景 | 建议响应等级 |
 | --- | --- | --- |
 | EP-01 | 核心业务不可用或大面积业务失败 | I/II |
 | EP-02 | 关键网络、通信或业务链路中断 | I/II |
 | EP-03 | 敏感数据疑似泄露、越权访问或数据外发 | I/II |
 | EP-04 | 数据篡改、丢失或备份恢复异常 | I/II |
 | EP-05 | 入侵攻击、恶意代码或横向扩散 | I/II |
 | EP-06 | 批量终端离线、高危终端或未授权设备接入 | II/III |
 | EP-07 | 身份认证、账号或证书体系异常 | II/III |
 | EP-08 | 核心主机、数据库、存储或资源耗尽故障 | I/II |
 | EP-09 | 数据源、采集链路或态势平台故障 | II/III |
 | EP-10 | 机房、电力、环境或灾备切换事件 | I/II |

### 8.2 统一预案模板

每份预案至少包含：

1. 适用范围、场景定义、业务重要性和关联系统。
2. 触发条件、排除条件、响应等级和启动授权人。
3. 指挥关系、值班人员、业务负责人、安全负责人、运维负责人、审计人员及替补人员。
4. 首个十五分钟动作清单：确认事实、建立事件群组、初步定级、保护证据、遏制扩散、发出初报。
5. 遏制步骤：隔离对象、限制访问、暂停风险操作、切换备用链路/服务、保留原始证据。
6. 根因分析和恢复步骤：修复、回滚、恢复备份、切换灾备、配置核查和安全加固。
7. 升级/降级条件：影响范围变化、超时未恢复、证据表明风险扩大、资源不足或出现次生影响。
8. 通知和沟通：内部通知对象、值班通讯录、业务用户提示、上级/监管通报条件和口径。
9. 恢复验证：业务功能、数据一致性、权限有效性、安全策略、监控恢复和用户验证。
10. 回退方案：恢复失败时的备用路径、回滚条件、回滚责任人和数据保护要求。
11. 关闭和复盘：终报、证据归档、根因、整改项、责任人、截止时间和演练改进。

### 8.3 典型场景处置要点

| 场景 | 首个十五分钟 | 遏制与恢复重点 | 关闭前验证 |
 | --- | --- | --- | --- |
 | 核心业务不可用 | 确认影响范围、应用/数据库/网络分层定位、通知业务负责人 | 切换备用、回滚变更、恢复服务、控制重试风暴 | 关键流程成功、数据一致、SLA 恢复 |
 | 敏感数据疑似泄露 | 固定证据、确认数据和账号范围、暂停可疑访问并初报 | 封禁会话/账号、控制外发、审查访问路径、评估影响 | 权限收敛、数据范围确认、无持续外泄 |
 | 入侵或恶意代码 | 隔离受影响资产、保留镜像/日志、阻断恶意通信 | 清除风险、修复漏洞、凭据轮换、分批恢复 | 安全扫描、策略有效、横向风险解除 |
 | 批量终端异常 | 按版本/区域/人员聚合，识别共同原因 | 隔离高危终端、暂停异常策略、恢复终端服务 | 在线率、模块状态、人员归属和风险均确认 |

 | 数据源/平台故障 | 标记数据不可用，确认影响的页面和报告，启用人工值守 | 修复接入、断点补传、重放校验、修正报告标记 | 数据完整性、时序、重复和报告准确性验证 |

### 8.4 告警到预案的处置映射

应急预案不能只按“系统故障”编写，而应把可发现的告警绑定到具体处置流程。每条告警规则至少关联：预案编号、触发条件、事件升级条件、首个动作、执行方式、责任人、完成时限、验证指标和回退方案。

| 告警/现象 | 关联预案 | 自动执行 | 人工执行 | 需要审批的动作 | 恢复验证 |
 | --- | --- | --- | --- | --- | --- |
 | 密信发送失败率持续升高 | EP-01 | 聚合失败请求、创建事件、通知值班人员、持续探测 | 检查网关、服务、数据库和链路；抽样发送/接收 | 生产回滚、切换服务、暂停非关键批量任务 | 连续多个窗口成功率恢复，消息无重复/丢失 |
 | 签阅待办增长或节点超时 | EP-01 | 统计积压、标记超时、生成催办任务 | 业务负责人确认影响和责任节点，安排催办或改派 | 修改流程节点、批量改派、启用备用流程 | 待办下降，关键文件完成，处理时效恢复 |
 | PIN 连续失败/身份密钥异常 | EP-07 | 限制重试、锁定会话、生成核验任务 | 核验人员身份、终端、介质和操作原因 | 解锁账号、重置凭据、替换密钥介质 | 身份核验通过，重新认证成功，审计完整 |
 | 证书临期或已过期 | EP-07 | 按 30/7 日发送提醒、生成轮换工单 | 确认使用范围、安排维护窗口和验证 | 签发/替换生产证书、撤销旧证书 | 登录、加解密、业务调用和证书链验证 |
 | 单台或批量终端离线 | EP-06 | 聚合区域/版本影响、通知责任人、标记覆盖不足 | 检查电量、网络、进程、策略和设备归属 | 批量隔离、策略下发、版本回退 | 心跳恢复、模块正常、人员可使用业务 |
 | 境外链路高利用率或中断 | EP-02 | 连续探测、记录峰值、通知通信责任人 | 判断业务影响、流量来源和链路故障原因 | 限制非关键流量、主备切换、调整路由 | 关键业务连通、时延/丢包/利用率回到基线 |
 | 异常下载、外发、解密或异常登录 | EP-03/EP-05 | 固定日志和会话证据、提升事件等级候选、通知安全人员 | 核验人员、终端、文件、来源/目标和是否本人操作 | 封禁账号、隔离终端、阻断外发、凭据轮换 | 风险路径关闭、无持续外泄、权限和策略复核通过 |
 | 数据库连接/队列/资源持续超限 | EP-08 | 采集快照、触发容量和性能告警、创建工单 | 分析慢查询、进程、容量、最近变更和业务影响 | 主备切换、回滚变更、扩容、重启生产组件 | 数据一致、业务调用正常、备份和监控恢复 |
 | 数据源陈旧、接口失败或报告生成失败 | EP-09 | 标记数据不可用、停止错误汇总、通知数据提供方 | 修复接口、核查字段、补传和重放数据 | 重新导入、修正已发布报告、调整来源配置 | 数据完整、无重复/乱序、报告重新核验并留痕 |

处置链示例：

```text
签阅节点超时告警
    -> 系统自动聚合同一节点和时间窗口的超时记录
    -> 自动生成关注告警并通知值班人员
    -> 值班人员确认是否达到业务影响条件
    -> 业务责任人判断是否启动 EP-01
    -> 人工催办或改派；涉及流程配置变更时走审批
    -> 系统持续计算待办量和节点停留时长
    -> 业务责任人确认文件办结和时效恢复
    -> 值班人员关闭事件，形成整改/复盘记录
```

### 8.5 处置自动化等级

建议将处置动作分为五级，并在每条预案中逐项标注：

| 等级 | 适用动作 | 执行要求 | 例子 |
 | --- | --- | --- | --- |
 | L0 记录 | 接收、解析、归档、更新指标 | 系统自动执行，不改变业务状态 | 保存原始告警、更新时间和证据索引 |
 | L1 通知 | 告警聚合、建单、提醒、值班通知 | 系统自动执行，失败必须重试并告警 | 发送失败率升高后创建事件和通知 |
 | L2 低风险自愈 | 可逆、范围明确、对业务影响可控的动作 | 事先授权，配置白名单、次数上限、超时回退 | 限制 PIN 重试、重启采集代理、重新探测链路 |
 | L3 人工确认执行 | 可能影响业务或涉及对象判断的动作 | 系统给出建议，责任人确认后执行 | 催办改派、切换备用链路、隔离单台终端 |
 | L4 审批/指挥执行 | 高风险、生产性、批量性或不可逆动作 | 授权审批、双人复核、全程审计和回退方案 | 批量禁用账号、批量隔离终端、生产回滚、对外通报 |

自动化处置必须同时具备以下条件，缺一项则降级为人工执行：

- 触发条件明确，误报率可接受，作用对象和范围可确定。
- 动作已预先授权，权限最小化，不能借自动化绕过审批。
- 动作可回退，设置次数、范围、时间和并发限制。
- 执行前保存必要证据，执行中记录每一步，执行后自动验证结果。
- 连续失败、影响扩大、超过时限或出现次生影响时，自动停止并升级人工处置。
- 对人员、敏感数据、核心业务和生产环境的动作默认采用 L3/L4，不采用无审批的批量自动处置。

### 8.6 预案执行记录

每次预案启动都应形成一个可追踪的预案实例，至少记录：

1. 触发告警、关联事件、启动时间、启动人和当前响应等级。
2. 自动动作及其规则版本、执行结果、失败重试和停止原因。
3. 人工任务、责任人、接收时间、完成时间、处置结果和证据。
4. 审批动作、审批人、审批意见、双人复核人和回退点。
5. 通知对象、通知渠道、送达状态、初报/续报/终报版本。
6. 恢复验证指标、业务负责人确认、安全负责人确认和审计复核。
7. 未完成任务、遗留风险、复盘结论、整改期限和验证结果。

预案不能以“告警消失”作为自动关闭条件。自动恢复只表示监测指标恢复，还必须确认业务功能、数据一致性、安全风险、用户影响和遗留任务均已处理。

## 9. 系统功能与建设分期

### 一期：统一基础和可追溯闭环

目标：先让系统“数据说得清、事件管得住、报告出得来”。

重点建设：

- 来源、资产、人员、账号、服务和事件统一编码及字段字典。
- 指标目录、口径登记、数据质量状态和来源健康。
- 统一事件中心：告警聚合、人工研判、分级、上报、处置、恢复和关闭。
- 日报、周报、月报模板、生成、审核、发布、版本和审计。
- 首批场景预案以文档和清单方式固化，支持人工执行和留痕。

### 二期：联动处置和流程执行

目标：让事件从“登记”进入“协同处置”。

重点建设：

- 业务、安全、终端、运维来源适配器和历史补数。
- 通知渠道、值班通讯录、工单系统和审批系统联动。
- 预案实例化、任务分派、超时提醒、升级和进度跟踪。
- 证据附件/引用、恢复验证、终报和复盘整改管理。
- 事件、服务、资产、人员和账号的关联查询。

### 三期：关联分析、自动编排和持续演练

目标：从“流程电子化”提升到“跨域研判和持续改进”。

重点建设：

- 跨域事件关联、影响范围推演、风险趋势和重复根因分析。
- 规则编排、低风险动作自动化和高风险动作审批执行。
- 预案数字化演练、演练评分、响应时长分析和改进闭环。
- 面向管理层的风险预测、资源容量和治理效果评价。
- 按制度要求完善灾备、审计、等保/合规证据和离线部署验证。

## 11. 会议决策清单

会议建议至少形成以下明确结论：

1. 系统正式名称、建设目标、纳入范围和不纳入范围。
2. 五域及平台运行保障的责任部门、负责人和替补联系人。
3. 首批纳入的业务系统、安全系统、终端平台、运维来源和数据提供计划。
4. 日报、周报、月报的接收人、审核人、发布时间、发布渠道和保密范围。
5. 核心指标目录、指标口径、统计周期、权威来源和缺数处理规则。
6. 异常事件分类、四级名称、分级标准、初报/续报/终报时限和越级上报条件。
7. 事件台账是否统一纳入业务、安全、终端、运维和平台运行事件，以及跨域事件的主责归属规则。
8. 首批上线的预案场景、启动授权人、值班组织、通知渠道和工单/指挥系统。
9. 高危处置动作的审批、双人复核、回退和审计要求。
10. 一期建设范围、里程碑、验收指标、预算/人员和后续二期输入。

## 12. 建议验收指标

以下指标作为讨论基线，正式数值由会议确认：

- 报告指标有来源、公式、时间窗口和责任人的覆盖率达到 100%。
- 纳入范围内的核心数据源有负责人、接入方式、更新时间和健康状态记录的覆盖率达到 100%。
- I/II 级事件具备完整事件编号、影响范围、责任人、上报记录、处置记录和恢复验证记录的比例达到 100%。
- 事件初报、续报、终报时限可统计，超时事件可自动提醒并形成审计记录。
- 首批预案至少完成一次桌面推演，核心角色、通知链路、证据保全和恢复验证均有记录。
- 重大事件关闭前必须完成业务恢复确认、安全风险确认和审计留痕，不能只以“告警消失”作为关闭条件。
- 报告生成失败、数据源中断、接口延迟和数据质量异常均能被识别、提示和纳入运行记录。
- 高危操作、权限变更、报告导出、事件等级调整和事件关闭均可追溯到操作人、时间、理由和审批记录。

## 13. 后续落地输入

会议通过后，按以下顺序转化为实施任务：

1. 固化制度：事件分类分级、上报时限、值班职责、报告制度和预案管理办法。
2. 建立台账：系统清单、数据源清单、指标字典、资产/人员/服务主数据和首批事件目录。
3. 输出产品需求：报告中心、事件中心、预案中心、通知工单、数据质量和审计功能。
4. 输出技术设计：数据库模型、接口契约、接入适配器、权限模型、消息通知和留存策略。
5. 先用四类场景验证闭环：核心业务中断、敏感数据疑似泄露、大面积终端异常、核心主机/网络故障。
6. 根据试运行结果调整阈值、分级、报告模板和预案动作，再进入自动化和跨域关联建设。

## 附：现有工程能力与本方案的衔接

当前工程已具备综合、安全、业务、终端、运维主题态势展示，运维/终端数据接入和事件沉淀，以及三员分立、审批和审计基础。后续建设应优先复用已有 `Situation` 统一展示模型、运维告警/接入模型、终端事件模型和 IAM 审计模型。

同时需要明确：当前部分主题态势数据仍为 Mock 或占位数据，不能直接作为正式报告指标。每项真实指标和事件都应在接入台账中补充来源、字段映射、统计口径、数据质量和敏感数据要求后再纳入正式报告和管理决策。
